# 代码评审

只评审，不直接改文件；用户明确要求“顺手修”时才进入修改流程。

1. **拿到改动面**：用 `gitstatus` / `diff` 或用户提供的 patch 看完整 diff；先确认基线分支、未跟踪文件和生成文件，避免漏看。
2. **按风险分层**：
   - P0：会导致数据损坏、安全问题、Win7 无法启动、编译/测试失败、权限绕过；
   - P1：逻辑错误、并发/资源泄漏、兼容性回退、错误被吞；
   - P2：可维护性、命名、注释、测试缺口、性能小问题。
3. **逐文件核对**：每个发现给 `路径:行号 — 问题 — 触发条件 — 建议改法`；没有证据的猜测标成“待确认”，不要伪装成结论。
4. **重点检查**：边界条件、错误处理、nil/空值、并发共享状态、超时/取消、路径穿越、密钥/日志泄漏、序列化兼容、测试是否真的覆盖改动。
5. **验证结论**：能在本地跑的最小构建/测试/静态检查就跑；跑不了时说明原因，不要用“看起来没问题”代替验证。
6. **输出**：先给“是否可合并/必须修什么”，再列 findings；不要按文件流水账复述 diff。
7. **不扩大范围**：不顺手重构、不格式化无关文件、不把评审变成需求讨论。

如果 diff 太大：先按改动类型/目录分组，优先看核心逻辑与安全边界，明确说明哪些部分没看。
