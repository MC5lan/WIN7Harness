# 缺陷复现与修复

1. **拿到可重复的证据**：记录用户给的命令、报错、输入、环境和期望结果；信息不足时先问最少的一个问题。
2. **写失败测试或最小复现**：优先在现有测试框架里加一个会失败的用例；做不到时用独立小脚本/最小输入复现。修复前先看到它失败。
3. **缩小范围**：用 `grep` / `code_search` / `calls` 从报错点向上追；一次只验证一个假设，不要同时改多处。
4. **修根因**：只改导致失败的最小逻辑；不要顺手重构、改公共接口或吞掉错误。需要扩大范围时先说明理由。
5. **回归**：失败用例必须转绿；再跑受影响包和全量测试；涉及并发/超时的缺陷至少多跑几次。
6. **记录**：把复现条件、根因、修复点、验证命令写进结论；值得长期保留的坑用 `memory_save` 记录。
7. **不要**：删除/跳过测试、把断言改松、用 `panic`/`TODO` 占位、在未验证时宣称“已修复”。

如果无法复现：明确列出已排除的环境、版本、输入差异，并给出用户可执行的下一步，不要凭空猜一个修复。
