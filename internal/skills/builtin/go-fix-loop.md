# Go 修复闭环

1. **先跑一次再动手**：`go build ./...`；如果构建通过，再跑受到影响包的测试，不要一上来全量测试。
2. **只盯第一条错误**：带 `file:line:col` 的那一行决定去哪看。连续报错往往是同一个根因，不要一次改八处。
3. **定位定义**：用 `code_search` 查符号、`grep` 查调用点、`calls` 查谁在调用；确认改动面之前不要编辑。
4. **小步改**：用 `edit_file` 或 `apply_patch` 改最小片段；跨文件改动先 `dry_run` 预览。不要为了让编译通过而删测试、注释报错或改 `go.mod` 版本逃避问题。
5. **定向回归**：`go vet ./...`，然后跑受影响包测试；通过后再跑全量 `go test ./...`。
6. **卡住就换证据**：同一命令失败两次就换方案；读完整错误、看最小复现、查工具链版本，不要原样重试。
7. **收尾**：说明改了哪些文件、跑了什么命令、哪些用例没覆盖。把确认过的构建/测试坑写入项目记忆。

Win7 特别注意：`386` 交叉编译、`GO386`、路径长度、控制台 GBK 乱码都可能伪装成代码错误，先用 `toolchain` 和 `diagnostics` 排除环境问题。
