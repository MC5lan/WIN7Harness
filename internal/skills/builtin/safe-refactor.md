# 安全重构

1. **先声明边界**：这次只改什么、不改什么、哪些公共 API 必须保持兼容；用户没说清时先确认验收标准。
2. **建立基线**：跑一次构建与相关测试，记录结果。基线本来就红时先说明，不要把它算成重构引入的。
3. **找全引用**：用 `code_search` / `calls` 找定义、调用点、测试、文档和生成代码；不要只改当前文件。
4. **小步实施**：优先 `apply_patch dry_run` 预览；一次只做一类变更（先重命名，再拆文件，再改接口），每步都能编译。
5. **保持行为**：除非用户明确要求，不改变错误语义、默认值、日志格式和序列化字段；必须改时写进风险说明。
6. **验证**：`diagnostics` → 构建 → 受影响包测试 → 全量测试；涉及公共 API 时检查所有调用方。
7. **可回滚**：告诉用户改了哪些文件、如何回退；不要在同一轮顺手重写无关文件。
8. **收尾**：列出兼容性结论、遗留风险、未覆盖的调用方。需要时更新文档或项目记忆。

不要用“重构”作为顺手改需求、换依赖、改构建系统的理由；一次只交付一个明确的重构目标。
