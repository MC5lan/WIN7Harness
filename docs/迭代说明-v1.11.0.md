# v1.11.0：P2 三件事（批量任务 / 会话全文检索 / 耗时与 token 归因）

v1.10.0 补的是单次任务"跑得住"：断线能续、改坏能退、存档不膨胀。
这一版补的是"用起来成体系"：一次跑一串任务、在几百个会话里找回某句话、
以及回答那个每天都被问的问题——到底是模型慢，还是工具慢。

---

## 1. 命令行批量任务：`-script`

**问题**：`-run` 一次只能跑一句话。实际用法都是"早上把这五件事都做一遍"，
于是只能写 `.bat` 里连调五次。但这样每次调用都要重新加载配置、重新装配引擎、
重新建立连接，五个任务五份开销；更麻烦的是失败处理全靠 bat 的 `if errorlevel`，
写起来比任务本身还长。

**做法**：
- `internal/core/script.go` 负责任务清单的解析：一行一个任务，空行与 `#`、`//` 开头跳过。
- 四个占位符 `{{date}}`、`{{time}}`、`{{datetime}}`、`{{dir}}`：一份清单每天复用，
  不需要每天改日期。未知占位符原样保留，方便用户自己写 `{{path}}` 之类占位。
- 编码按 Win7 记事本的实际选择处理：UTF-8（含 BOM）与 UTF-16 LE/BE（带 BOM）都能读。
  **ANSI/GBK 明确报错并提示"另存为 UTF-8"**——拿乱码任务去执行比直接报错危险得多。
- `cmd/win7harness/run.go` 重构成 `runner`：引擎只装配一次，多条任务复用同一份引擎与连接。
  任务之间默认 `Reset()` 互相隔离，加 `-shared` 才让后一条沿用前一条的上下文
  （例如"先读这批文件，再根据内容写总结"）。
- 失败策略：默认**遇错即停**（后面的任务大概率依赖前一条的结果）；`-keep-going` 则继续跑完，
  最后统一汇总。超时直接中止整批——模型侧卡住时后面的任务大概率同样超时，白等没意义。
- 退出码沿用单任务的约定：0 全成功、1 有失败或没跑完、2 参数或清单问题、3 超时。
  汇总逻辑抽成 `core.SummarizeScript` 单独测试，因为批处理脚本普遍靠退出码判断成败，
  这里错一次会连累所有自动化。
- text 模式每条任务前打印 `[2/5] 任务内容`，答复逐条打到标准输出，结尾一行汇总；
  `-json` 输出 `{"ok":..., "tasks":[...], "summary":{...}}`，便于流水线解析。

**验证**：`internal/core/script_test.go` 覆盖清单解析（注释/空行/CRLF/行号）、占位符替换、
三种编码（UTF-16 LE/BE、UTF-8 BOM、GBK 报错）、汇总退出码四种组合。

## 2. 会话全文检索：`/find` + `/open`

**问题**：左栏搜索框是"过滤会话列表"，每个会话只露第一处命中。真实诉求是：
"上次那条 `ERR_CONNECTION_RESET` 我是在哪句话里说的？"——需要的是命中位置、上下文片段、
按相关度排序，并且能一键跳过去。现有实现三样都缺。

**做法**：
- `internal/core/find.go` 只做纯计算，便于跨平台单测：输入会话文档，输出命中列表。
- 匹配范围不止对话正文，还包括**工具参数与工具输出**。报错原文、命令参数往往只出现在
  工具卡片里，不搜这块就会出现"我明明见过这句报错却搜不到"。
- 多个关键词是"与"：同一条消息里全部出现才算命中。查 `connection reset` 时，
  只提到 connection 的消息会淹掉真正要找的那条报错。
- 标题命中加权 3 分：标题是人工摘要，命中标题通常就是用户要找的那个会话；
  纯标题命中也会生成一条结果（`MsgIdx=-1`），否则"搜自己起的标题搜不到"。
- 排序：相关度优先，同分时新消息优先——找"最近那次"比找半年前那次更常见。
- 界面侧 `internal/app/find.go`：`/find 关键词` 列出前 30 条（会话标题 + 来源 + 时间 + 片段），
  结果缓存进 `a.findHits`；`/open 序号` 切换会话并滚动到那条消息。
- 跳转的定位问题：滚动条是按像素的，而排版才知道每条消息的 y。做法是设 `jumpMsg`，
  下一帧 `layoutSession` 完成、`laySegs` 就绪后计算 `msgTopOffset` 并设置滚动位置，
  所以长会话里跳转也落在正确位置，不是"跳到差不多的地方"。
- 片段用 Markdown 引用块包起来，并替换反引号与竖线：缩进两格会被当成续行、
  四格会变代码块，含表格竖线的片段会把整段渲染搞乱。

**验证**：`internal/core/find_test.go` 覆盖相关度排序与 limit、同分新消息优先、
多词"与"语义与大小写不敏感、工具输出命中标记、UTF-8 片段边界不切出现半个汉字、标题加权。

## 3. 耗时与 token 归因：`/stats`

**问题**：/status 只给总数，用户问"为什么这轮这么慢"，答不上来。慢可能是模型在思考、
可能是某个工具（列大目录、跑命令）在阻塞，也可能是 token 太多导致每轮都慢，三种原因对策完全不同。

**做法**：
- `internal/agent/stats.go`：按工具聚合（次数、总耗时、平均、最慢、失败数），
  按模型轮次聚合（耗时、输出 token、最慢一轮）。
- 归因切分点是**模型在想 vs 工具在做**：模型调用耗时包住 `Client.Chat` 整段（含流式接收），
  工具耗时在 `execBatch` 的出口按单个调用记录，并行批次里各工具分别计时，不会把
  并行等待算到某一个工具头上。
- `tool_end` 事件新增 `Dur` 字段。界面显示的耗时改用引擎测出的真实值，而不是自己
  `time.Since`——事件跨 goroutine 送到界面有延迟，界面自己算会把渲染排队时间也算进工具耗时。
- `/stats` 输出：模型/工具耗时占比、生成速度（token/s）、模型调用轮次与每轮平均 token、
  按总耗时排序的工具 Top 8。`/status` 也加了一行耗时摘要。
- 测速用 completion token ÷ 模型耗时，只统计模型段，工具时间不计入——否则跑了个慢命令之后
  生成速度会莫名其妙变慢。

**验证**：`internal/agent/stats_test.go` 覆盖聚合与排序、均值与最慢值、占比与速度文案、
空统计提示、Top N 截断。

## 一处顺手的修正

`execBatch` 的返回值从 `[]string` 变成 `([]string, []time.Duration)`，
`internal/agent/selftest_test.go` 相应更新，并顺带断言耗时数组长度与调用数一致。

## 升级说明

- 配置与会话文件格式未变，直接覆盖 exe 即可，旧会话无需迁移。
- 新增命令行参数 `-script`、`-keep-going`、`-shared`，不影响既有 `-run` 用法。
- 新增命令 `/find`、`/open`、`/stats`，都已进命令面板与 `/help`。
