WIN7 Harness v1.29.0 忽略错误审计

审计范围：internal/ 与 cmd/ 下全部 .go 文件里显式丢弃返回值（`_ = ...`）的位置。

盘点结果：合计 199 处，其中生产代码 192 处、测试代码 7 处。

方法：先按"丢掉了会怎样"分类，再逐类判断是修、是留。
判据只有一条——这个失败会不会让用户少东西、看到假象、或者丢掉救回来的机会。
不会的，就不为它加分支：代码里每一处错误处理都该有明确的补救动作，没有动作的错误处理只是噪音。

----------------------------------------------------------------
一、分类统计（生产代码）
----------------------------------------------------------------

  类别            数量    说明
  清理类          18      os.Remove / os.RemoveAll
  写盘类          20      os.WriteFile / writeFileAtomic / json 编码到响应体
  目录创建        3       os.MkdirAll
  入参解析        3       json.Unmarshal / NewDecoder（手机接口请求体）
  外部进程        3       exec / cmd
  其它            142     关闭句柄、Setenv、类型断言、故意忽略的返回值等
  ------------------------------------------------------------
  合计            192

测试代码 7 处（写盘 2、解析 1、其它 4）：全部是"故意写坏文件/返回错误响应"来造用例，
忽略返回值本身就是用例的一部分，不改。

----------------------------------------------------------------
二、本版修掉的 6 处
----------------------------------------------------------------

1) internal/app/store.go — 会话 .bak 备份写失败（2 处）
   旧：`_ = writeFileAtomic(bak, old)`
   问题：备份没写成仍然照写主文件，等于把"上一版可回退"的兜底悄悄摘掉了，
        而且没有任何痕迹，事后无法判断这次覆盖是不是"没有后悔药的那次"。
   新：备份失败写日志（含源文件名），主流程继续（不因备份失败挡住保存），
       但日志里能查出哪次保存是裸奔的。

2) internal/app/commands.go — /eval 报告落盘（2 处：MkdirAll + WriteFile）
   旧：忽略错误后无条件输出"报告：<路径>"。
   问题：目录不可写或磁盘满时，用户按这个路径去找是空文件，以为评测成功。
   新：区分"评测完成"与"报告未能落盘"，后者直接带上错误原文。

3) cmd/win7harness/eval.go — 评测 CLI 的 JSON 报告（2 处：MarshalIndent + WriteFile）
   旧：无论成没成都把 js 路径打印出来。
   问题：同 2)，脚本里 `eval-report.json` 被下游读取时会拿到不存在或旧的旧文件。
   新：序列化失败与写入失败分别报错；未生成时明确打印"（JSON 版未生成）"，
       md 报告成功仍照常打印路径。

----------------------------------------------------------------
三、有意保留及理据
----------------------------------------------------------------

  · 崩溃/启动标记（internal/core/crash.go，3 处 os.WriteFile）
    丢掉只影响"上次是否非正常退出"的判断，最坏结果是少提示一次上次崩溃，
    不影响任何数据正确性。为它加错误分支没有补救动作。

  · 技能"已提示过"标记（internal/skills/skills.go:298）
    写不成最多下次再提示一遍，属于幂等的良性重复。

  · HTTP 响应编码（internal/remote/server.go:504 等）
    对端已经断开，编码失败时没有可执行动作；此时改状态码或重试都无意义。

  · 清理类 18 处（os.Remove / RemoveAll）
    删除失败的实际后果是"残留文件多占几 MB"。为它中断主流程（例如保存会话、
    更新索引）得不偿失；需要用户知道的清理动作（如 /queue clear、/device prune）
    走的是有返回值的路径，另有回执。

  · 目录创建 3 处
    均为"先建再写"，紧随其后的写操作会暴露真正的失败原因，重复判断反而掩盖根因。

  · 手机接口入参解析 3 处
    解析失败后紧接的字段零值校验会返回 400，错误已被覆盖，不必两处都报。

  · 其它 142 处
    主要是 defer f.Close()（只读文件）、`_, _ =` 形式的多返回值忽略、
    以及把返回值当"是否存在"用的探测式调用。

----------------------------------------------------------------
四、没有做的事（明确记录）
----------------------------------------------------------------

  · 没有把 199 处一律改成 if err != nil 加日志：
    日志本身也是 I/O，在低配 Win7 上高频路径加日志会拖慢主流程，
    且大量"无补救动作"的日志会把真正有用的报错埋掉。
  · 没有引入第三方错误处理库：与本产品零依赖底线冲突。
  · 未覆盖 panic 恢复点以外的 goroutine 级错误传播（当前架构下 goroutine 内部
    错误统一回传主循环，已由 agent 包的 errCh 承担）。
