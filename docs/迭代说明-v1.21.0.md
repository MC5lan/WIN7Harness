# WIN7 Harness v1.21.0 迭代说明：技能、增量索引、评测基线

## 一、这一版解决什么

v1.20 把"方案—执行—回退"这条主链路收口了，剩下三个短板都在**效率**上：

1. **重复交代**：每次开新会话都要把"这个项目怎么跑测试、发版要打哪几个包、
   代码风格是什么"再说一遍。模型不记得，用户烦。
2. **索引只会全量**：改完一个文件想看新函数，得等整库重建；大仓库虽说不慢，
   但"改一行→重建全库"心里总归别扭。
3. **没有回归闸门**：每版都靠人肉点界面确认"好像没坏"，改坏一个用例也没人知道。

这一版对应三件事：**技能（Skills）复用做法、索引脏文件增量、评测基线可量化**。

## 二、技能 Skills（internal/skills）

技能就是一份 Markdown 流程文档，落在约定目录即被自动发现：

```
<工作目录>\.harness\skills\<技能名>\SKILL.md     项目级（随仓库走）
<工作目录>\.harness\skills\<技能名>.md           项目级，单文件形式
%APPDATA%\Win7Harness\skills\<技能名>\SKILL.md   全局（跨项目）
```

文件头是可选的简单属性，后面就是正文：

```
---
name: go-fix-loop
description: Go 编译失败的定位与修复
when: 改完 Go 代码需要验证时
---
1. 先 go build ./...
2. 读第一条错误，用 code_search 定位
3. 小步改，改完 go test ./...
```

设计取舍：

- **注入只给清单，不给全文**。`buildContext` 里拼的是"名字 + 用途"，正文要模型
  自己用 `skill_use` 取。技能多的项目不会一次吃掉几千 token，也不会因为无关技能
  干扰当前任务。
- **同名覆盖**：项目级优先于全局，同一个技能名在不同仓库可以有不同做法。
- **宽松解析**：没有 frontmatter 也能用（名字取文件名，用途取正文首行），
  降低门槛；有 frontmatter 则严格取三个字段。
- **首次启动投放示例**：全局目录为空时生成 `go-fix-loop`，并写 `.sample-created`
  标记——只投一次，用户删了不会再冒出来。

配套命令：`/skills` 看清单，`/skill 名称` 手动加载；工具侧是 `skill_list` 与
`skill_use`，模型自己也能查、能取。

## 三、索引脏文件增量（internal/codeidx + agent 接线）

原来 `Update` 靠 mtime + size 判断"变了没"，但**同一秒内改两次**或**改完大小不变**
都会漏判。这一版在"谁改的"这一侧补上确定性：

- `MarkDirtyAbs(file)` / `MarkDirtyRel`：把文件登记为脏；
- 引擎在工具成功后按类型接线：`write_file` / `edit_file` / `delete_file` 精确登记单个
  文件；`apply_patch` 与 `run_command` 改不清范围，直接整库 `MarkStale`；
- `Build` 里脏文件绕过 mtime 复用强制重解析，并累加 `Dirty` 计数。

`BuildStats` 现在给出 `Total / Reused / Parsed / Dirty / Removed / Incremental / ElapsedMs`，
`/index` 直接回显："增量：复用 74 个文件、重解析 1 个（其中刚被改动的 1 个）、
消失 0 个，耗时 9 ms"。`/index inc` 走增量，不带参数仍是全量重建。

这样"改完立刻查符号"拿到的行号一定是新的，不会出现"代码里明明有，索引说没有"。

## 四、评测基线 Eval（internal/eval + cmd/evalrun + 界面 /eval + 命令行 -eval）

9 个不依赖模型的用例，压的是**工具链与底座**，跑一次不到 100ms：

| 编号 | 用例 | 压什么 |
|---|---|---|
| B01 | 写文件逐字节正确 | 编码、换行、中文 |
| B02 | 精确替换唯一匹配 | edit_file 不误伤其他位置 |
| B03 | 补丁 dry_run 不落盘 | apply_patch 预演安全 |
| B04 | grep 行号准确 | 内容检索定位 |
| B05 | 分段读取范围 | 大文件 offset/limit |
| B06 | 索引增量同步 | 脏文件强制重解析 |
| B07 | 命令输出回传 | 子进程管道不丢字节 |
| B08 | 技能发现与加载 | skills 扫描与正文 |
| B09 | 删除后一致性 | 文件消失、索引不残留 |

关键点：

- **用例要能抓住回归**。做完加了一条变异测试：故意把脏文件强制重解析去掉，
  B06 立刻失败（8 通过 1 失败），证明它不是"永远绿"的假闸门。
- **端到端不混进基线**。要真模型改代码的用例依赖网络、token、模型随机性，
  放进来自动化就变噪声，基线只留确定性部分。
- 三个入口共用一套用例：界面 `/eval`、命令行 `-eval`（退出码 0/1/2，可接 CI）、
  `cmd/evalrun`（发版时出报告）。

## 五、自检扩到 22 项

新增三项，全部真跑不给假绿：

- **ST20 技能发现与加载**：真建一个技能目录、写 SKILL.md、扫描、取正文、
  校验系统提示里出现了它，最后清理。
- **ST21 索引增量与行号同步**：写文件→全量索引→改文件→MarkDirty→增量→
  断言新符号出现且行号为 5、脏文件被计数。
- **ST22 评测基线可执行**：在沙箱里跑一遍 9 个用例，有失败就报失败编号。

Linux 本机实跑：22 项通过 20、失败 0、跳过 2（无 GDI 渲染层、未配模型）。

## 六、升级与兼容

- 版本号 1.21.0，配置结构无破坏性变更，旧的 `config.json` 与历史会话直接可用。
- 新增目录 `%APPDATA%\Win7Harness\skills`、`%APPDATA%\Win7Harness\eval`，
  首次使用自动创建。
- 技能目录不存在完全不影响使用（清单为空、不注入任何内容）。
- 双架构包照旧：`WIN7Harness-amd64.exe` / `WIN7Harness-386.exe`，
  Win7 SP1 + KB2533623 + KB4474419，纯静态单文件。
