WIN7 Harness v1.26.0 迭代说明
================================================================

版本定位：把 v1.25 的"能干活"补成"能长时间干活、出了事也不乱来"。
三个方向：
  P0 让它扛得住长任务与坏网络——后台跑任务、按规则审批、工具调用不再一断就废；
  P1 让它按项目自己的规矩干活——自定义子代理、补丁逐段审阅；
  P2 让它记住这个项目、能分身试方案、接得上远程工具、故障能自证。

适用环境不变：Windows 7 SP1 + KB2533623 + KB4474419，单文件 exe，零运行库依赖，
不装 .NET、不装 VC++、不写注册表。
包名：WIN7Harness-v1.26.0-win7.zip（内含 x86 / x64 双架构 exe、README、setup.bat）。

----------------------------------------------------------------
一、P0-1 后台任务与进程托管
----------------------------------------------------------------

过去：run_command 同步等待，一条 `go build` 卡住就整轮干等；超时上限 1800 秒，
      超时之后子进程的子进程可能还留在后台。
现在：run_command 支持 background=true，立刻返回任务 ID，不再阻塞对话。

  · 四个工具分工明确：
      task_output  —— 增量读输出（返回偏移量，下次传 from= 只拿新内容）；
      task_list    —— 所有后台任务、命令、状态、耗时；
      task_kill    —— 终止任务，连带它的子进程；
      run_command background=true —— 起任务。
  · 输出按环形缓冲保留尾部（默认保留最近 128KB），长时间刷屏的日志不会把内存吃光；
    读取时超长只留尾部，因为报错信息通常在最后。
  · 进程托管：Windows 上子进程挂进 Job Object（JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE），
    kill 时 TerminateJobObject 一次性收掉整棵进程树——不会出现"exe 关了、孙子进程还在"；
    Linux/macOS 走进程组，行为一致。
  · 状态页会显示还有几个后台任务在跑，长任务不用翻记录找。

----------------------------------------------------------------
二、P0-2 权限与审批策略
----------------------------------------------------------------

过去：只有"高危操作弹一次确认"+ 一个自动执行开关，两头都不好用——
      想放行一类只读命令得全放开，想收紧又只能逐个弹窗。
现在：规则 + 模式 + 目录白名单三层组合。

  · 规则三种动作：allow（直接放行）、deny（直接拒绝）、ask（问一次），
    形如 `allow:run_command:git status`、`deny:run_command:format *`、
    `ask:write_file:*.env`。前半是工具名，后半是目标匹配（支持 * 通配）。
  · 判定优先级固定：deny > allow > 高危 > ask > 模式默认。deny 永远赢，
    避免"某条 allow 写宽了，把删除也放过去"。
  · 三种模式：
      plan  只读——写盘、执行一律拒绝，适合"先让它看明白再动手"；
      ask   默认——写盘与执行逐次确认（老行为的加强版）；
      auto  自动——工作区内放行，越界问，高危仍问。
  · 目录白名单：允许写工作区之外的指定目录（如共享盘、另一个仓库），
    白名单内的写入不再逐次确认。
  · /perm 一条命令管全部：无参看当前策略与规则清单、`/perm mode auto` 切模式、
    `/perm add allow run_command:go test *` 加规则、`/perm del 2` 删规则、
    `/perm test run_command "rm -rf x"` 试判（不执行，只看会怎么判）。
  · 策略持久化在配置文件里，重启后仍在；改模式、加规则即时生效。

三、P0-3 工具调用可靠性
----------------------------------------------------------------

过去：流式响应中途断线，模型已经吐了一半就整轮失败；参数 JSON 被截断时直接解析失败；
      遇到 429 就干等一个固定时长。
现在：三处都补上了。

  · 断线续写（ChatWithResume）：流被切断但已经收到正文时，把"已输出部分 + 续写指令"
    发回去让模型从断点写完，拼接成完整回复。
    不该续写的三种情况明确排除：已经收到工具调用片段（参数被截断时续出来的调用是错的）、
    用户主动停止、没有正文可续。
  · 429 / 5xx 退避：优先按 Retry-After 头的秒数等，没给头就指数退避（有上限），
    不会一次限流就打崩任务。
  · 工具参数修复（RepairToolArgs）：模型把 JSON 包在解释文字里、包在 markdown 代码块里、
    结尾括号缺一个、尾逗号多一个，都能先修再解析，解析不出来才报错。
  · 连续两次空响应（既无正文也无工具调用）明确报错，并提示是模型名/上下文长度问题，
    而不是静默返回空消息。

四、P1-1 自定义子代理
----------------------------------------------------------------

过去：子代理只有内置一种，工具权限一刀切。
现在：在项目里放一个 markdown 就能定义自己的子代理——<工作区>/.harness/agents/*.md：

    ---
    name: reviewer
    description: 只做代码审阅，不改文件
    tools: [read_file, grep]
    model: fast
    max_rounds: 6
    ---

    你只审阅，不改文件；发现问题按 文件:行 列出。

  · 头部字段：name（必需）、description、tools（工具白名单）、model（main/fast）、
    max_rounds（轮数上限）；正文就是它的系统提示词。
  · task 工具用 agent 参数指名调用：`task(agent="reviewer", prompt="...")`；
    不指定时走内置通用子代理，老用法不受影响。
  · 工具白名单是真的裁剪：没在列表里的工具它调不到，不是"提示它别用"。
  · 目录按 mtime 缓存，改了定义立即可用，不用重启。
  · 坏文件（没有头部、字段写错）只跳过并给警告，不影响其它定义。
  · /agents 列出当前项目可用的自定义子代理。

----------------------------------------------------------------
五、P1-2 补丁逐段审阅
----------------------------------------------------------------

过去：apply_patch 要么整份应用，要么 dry_run 看个大概，模型改十处有一处不对，
      也得整份重来。
现在：应用前按 hunk 编号，逐段挑。

  · dry_run 给出带编号的改动清单（哪个文件、第几段、改了什么）。
  · hunks="1,3-4" 只应用选中的段落，其余段落原样跳过——这就是逐段接受/拒绝的落地方式。
  · 编号在整份补丁内全局唯一，跨文件也能精确指定。
  · 没传 hunks 等价于全量应用，老脚本不用改。

六、P2 项目长期记忆
----------------------------------------------------------------

过去：每次新会话都要重新交代"这个项目怎么构建、跑哪个命令自检"。
现在：<工作区>/.harness/memory.md 存项目事实，自动进系统提示。

  · 三个工具：memory_save（记一条，可带 tag）、memory_search（关键词检索，
    多词部分命中即可）、memory_list（按时间倒序列全部）。
  · 存的是"踩出来的事实"：构建命令、产物路径、坑在哪、外部信息核对结果；
    与 AGENTS.md 的分工是——memory.md 记事实，AGENTS.md 记约定。
  · 每次会话自动把记忆块拼进系统提示，模型一开始就知道这个项目的规矩。
  · 纯文本 markdown，可手工编辑、可进版本库、可 review；写坏一行不影响其它条目。

----------------------------------------------------------------
七、P2 会话分叉（/fork）
----------------------------------------------------------------

想从同一出发点试两套方案，过去只能重开一个会话重新交代背景。
现在：/fork 把当前会话整段复制成新会话并切过去，原会话保持不动。

  · 消息、图片、模型选择、工作目录一并复制（切片按值复制，两支互不影响）；
  · 标题自动加后缀便于区分：`原题 · 分叉`，可加备注 `/fork 方案B`；
  · 长标题按字符截断，侧栏不会被撑爆；
  · 后续所有改动只写新会话，想回到原来那支直接切回去。

----------------------------------------------------------------
八、P2 远程 MCP
----------------------------------------------------------------

过去：MCP 只能起本地 stdio 子进程（npx / python 脚本），需要装运行时的机器用不了。
现在：配置里给 MCPServer 配 url 就走远程 HTTP，协议按 MCP Streamable HTTP：
      POST JSON-RPC + SSE 响应。

  · initialize 握手（带 protocolVersion 与 clientInfo）→ notifications/initialized →
    tools/list → tools/call，全套走标准流程；
  · 响应可能是 application/json 也可能是 text/event-stream，两种都解析；
  · 自定义请求头（Authorization: Bearer xxx 这类）配在 headers 里；
  · 连接复用 + 存活探测，断了在状态里显示"断开"并在 /status 里可见；
  · 本地 stdio 方式完全保留，两种可混用。

----------------------------------------------------------------
九、P2 代理与 TLS 诊断强化
----------------------------------------------------------------

过去：网络出错只回一句原始错误（`dial tcp 127.0.0.1:7890: connectex: ...`），
      用户不知道该改代理还是该装补丁。
现在：分层诊断 + 人话结论。

  · /netdiag 逐层探：DNS 解析 → TCP 连接 → TLS 握手 → HTTP 响应，
    每层给耗时与结论，最后一句人话总结 + 一条可执行建议。
  · 失败能定位到具体一层：域名解析失败会说"DNS 不可用或域名写错，可换 223.5.5.5"，
    而不是笼统"网络异常"。
  · 错误识别补齐 Windows 文案：`connectex: No connection could be made because the
    target machine actively refused it` 会被认成拒绝连接；对端是本机端口（7890/7897/1080
    等）时直接判定"代理软件没启动或端口不对"，而不是"目标端口没监听"。
  · 证书问题分开说：x509 / 证书链 / TLS 握手失败各有对应建议
    （Win7 缺 KB4474419 导致根证书不全是最常见的一类）。

十、P2 图片压缩与 OCR
----------------------------------------------------------------

过去：read_image 超过 8MB 直接拒绝发送，截图稍大就只能看元信息；图里的文字得人肉抄。
现在：

  · 压缩：max_side 指定长边上限（默认不缩），超过就等比缩放；
    缩放发生在传输前，模型收到的仍是真图，只是像素更省。
    尺寸是硬需求——缩过就一定生效，即使重编码后体积略有增加（像素少了就是省 token）。
  · save_compressed=true 时把压缩结果存盘（便于复用同一张图多次提问）。
  · OCR：ocr=true 调用本机 tesseract，ocr_lang 指定语言（默认 chi_sim+eng）；
    识别到的文字随结果一起返回，便于"截图里的报错"直接进上下文。
  · 没装 tesseract 不会让读图失败：图片照常发送，OCR 段落明确写"未安装"并给出安装指引。
  · 状态页显示 OCR 是否可用。

十一、自检与验证
----------------------------------------------------------------

自检用例从 44 项扩到 54 项，新增 10 项，全部走真实数据主路径（不 mock 关键环节）：

  ST45 后台任务与进程托管  真起后台命令、增量读输出、列表可见、终止后状态收敛
  ST46 审批策略与白名单    allow/deny/ask 命中、deny 优先、plan 只读、白名单越界放行、规则往返
  ST47 工具调用可靠性      4 种坏 JSON 全部修复；空响应恰好重试 1 次（共 2 次请求）
  ST48 自定义子代理定义    name/description/tools/model/max_rounds 解析；坏文件被跳过不阻断
  ST49 补丁逐段审阅        dry_run 清单完整；hunks=2 只改第二段，第一段保持原样
  ST50 项目长期记忆        写入 → 检索命中 → 清单完整 → 落盘 .harness/memory.md
  ST51 会话分叉隔离        标题规则与截断；两支追加消息互不污染，原会话不被写脏
  ST52 远程 MCP 传输       真 httptest 服务：initialize → tools/list → tools/call 全链路
  ST53 网络分层诊断        可达地址逐层通过；坏域名定位到 DNS 并给建议；Windows 文案错误人话化
  ST54 图片压缩与 OCR      2400×1600 压到长边 600 且仍附图；无引擎时 OCR 分支正常降级

结果：54 项，通过 51、失败 0、跳过 3（无 git 环境跳过 ST40；需真实模型/联网的检查在
离线沙箱跳过）。新增用例首轮暴露 4 个真实缺陷并修掉：后台任务 ID 解析、
白名单语义只对 auto 模式生效、Windows 拒绝连接文案未被识别、缩放被"体积没变小"逻辑吞掉。

编译与打包：
  · GOOS=windows GOARCH=386 与 amd64 双架构 go build ./... 全通过；
  · build.sh 双架构编译 + rsrc 嵌图标 + PE 资源校验 + ZIP 打包；
  · linux 侧 selftest_run 跑全套 54 项，作为出包前的回归闸门。

----------------------------------------------------------------
十二、升级说明
----------------------------------------------------------------

· 直接覆盖旧 exe 即可，%APPDATA%\Win7Harness 下的会话与配置无需迁移；
· 新增配置项（PermMode / PermRules / PermDirs）均有默认值，缺省等于 v1.25 的行为；
· 老会话里没有分叉信息，/fork 从当前会话即时复制，无需迁移；
· .harness/memory.md、.harness/agents/*.md 都是可选的：不存在时相关工具返回明确提示，
  其余功能不受影响；把目录删掉即可停用；
· MCP 配置新增 url / headers 两项，原有 command 方式的配置不改也能用；
· read_image 的 max_side / save_compressed / ocr / ocr_lang 全部可选，
  不传时行为与 v1.25 完全一致。
