# WIN7 Harness v1.20.0 迭代说明：计划模式闭环、失败诊断、改动回退

## 一、这一版解决什么

v1.19 补上了"能不能验证"，v1.20 补的是**用起来顺不顺**。三个最扎手的地方：

1. **计划模式半成品**：`/plan` 能拦住写工具了，但模型给出方案后，用户要自己
   再敲一遍 `/plan` 退出、再敲一遍"开始吧"——所谓"先看方案再动手"变成了两遍手工活。
2. **失败只会复述错误**：工具挂了就回一句 `错误：文件不存在: ...`，模型看到之后
   常常原样重试同一路径，或者开始猜；用户在界面上只看到一串报错，不知道卡在哪一类问题。
3. **回退只能一步一步**：`/undo` 退一步，改坏了五个文件就得按五次，而且看不见
   "我到底动过哪些文件"，退到一半心里没底。

这一版把三件事各自收口：方案给到就等一个回车；失败回灌带上原因与下一步；
改动可以列清单、一次退多步。

## 二、计划模式闭环

原来的 `PlanMode` 只是"写工具一律拒绝"，现在补上确认回环：

```
/plan  →  调研、读代码、只出方案（不写盘）
   ↓
模型给出编号方案 → 识别为"待确认方案" → 确认指令自动预填输入框
   ↓
用户回车 → 自动退出计划模式 → 开始实施
```

- **识别**（`internal/agent/plan.go`）：至少两条编号步骤（`1.` / `1)` / `1、` / `1:`），
  且正文长度达到阈值才认定为方案。判定刻意保守：**宁可漏判**（退化成普通回答，
  用户仍可手动 `/plan` 退出），**不要错判**（把普通答复当方案弹提示）。
- **确认**：方案事件到达后，输入框预填"按上面的计划开始执行"，状态栏提示
  "方案待确认：回车开始实施，或继续补充要求"；用户也可以直接改这段文字或继续追问。
- **自动退出**：发送时若文本以该确认语开头，引擎的 `PlanMode` 自动置 false。
  否则会出现"点了确认但写工具仍被拒"的错觉——这是最容易让人以为程序坏了的地方。

## 三、失败诊断与盲重试护栏（internal/agent/diagnose.go）

工具失败的返回从一句话变成三句话：

```
错误：文件不存在: C:\proj\main.go

[失败诊断] 目标文件或目录不存在
- 可能原因：路径拼错、文件被移走，或上一步没真正创建成功；Windows 下还要注意盘符与反斜杠。
- 建议下一步：先用 list_dir 或 glob 确认实际路径，再按真实名字重试；不要凭记忆猜路径。
```

原始报错永远放在最前面（模型和用户都要能读到原文），诊断只是追加。

覆盖 10 类病根：

| 类别 | 典型触发 |
| --- | --- |
| not_found | 文件/目录不存在、系统找不到指定的路径 |
| permission | 拒绝访问、文件被占用、越界或系统保护目录 |
| anchor | 待替换原文没匹配上、匹配不唯一 |
| command_missing | 不是内部或外部命令、executable not found |
| disk_full | 磁盘空间不足 |
| timeout | 超时、被用户中断 |
| encoding | 非 UTF-8、UTF-16、解析失败 |
| bad_args | JSON 非法、缺必填参数、类型不对 |
| guard | 计划模式拒绝、需确认、钩子阻止 |
| too_large | 文件过大、需分段读取 |

**盲重试硬护栏**：同一工具 + 同一参数指纹 + 同一诊断类别，
第 2 次失败给一次提醒（"先改变一个前提"），第 3 次直接拦下不执行，
返回"必须换方法：改参数、换工具，或停下来把情况告诉用户"。
参数指纹用 FNV-64a 对原始参数字符串取哈希，避免把长参数塞进比较逻辑。
工具只要成功一次，计数立刻清零——正常的多步修改不会误伤。

## 四、改动清单与多步回退（internal/core/checkpoint.go）

快照机制本来就有（写入/修改/删除前自动备份），这版把它变成用户能看见、能批量退的东西：

```
/checkpoints        列出本会话改过的文件，1 = 最新
/rewind 3           一次回退最近 3 步
/undo               等价于 /rewind 1（保留原命令）
```

清单里每条标注动作性质：

- `覆盖前备份` —— 回退会把文件内容恢复成改之前的样子
- `新建（回退将删除）` —— 该文件是本次会话新建的，回退即删除

`RewindSteps(n)` 逐步调用 `UndoLast()`，**中途失败即停**，并把"已经退掉的步数"如实
报回去，同时打印当前清单——退了一半不装作没发生，也不继续错误地往下退。

## 五、自检扩至 19 项

新增三项，都是"真数据验证"，不是编译通过就算数：

| 编号 | 用例 | 验的是什么 |
| --- | --- | --- |
| ST17 | 改动清单与多步回退 | 造两次改动 → 清单顺序正确 → 两步一起退 → 覆盖的还原、新建的被删 |
| ST18 | 失败诊断分类 | 5 类真实报错文案必须归到对的类别，且未知错误必须落到 unknown 而非误判 |
| ST19 | 计划方案识别 | 编号方案要认出；过短文本与普通回答不能误判 |

ST17 会真的写文件、写快照、再回退，跑完在沙箱内自清理。

## 六、顺手修掉的一个真实缺陷

`internal/tools/exec_other.go`（非 Windows 分支）里原来是先 `cmd.Wait()` 再等读取 goroutine。
Go 的 `cmd.Wait()` 会关闭 `StdoutPipe`/`StderrPipe`，与并发 `io.Copy` 撞上就会丢输出，
表现是**偶发**的"退出码 0 但输出为空"。这次跑自检时复现了一次（ST09）。

改为读完再 `Wait()`，之后 `-count=8` 连跑八轮自检全部通过。
Windows 分支用的是自建 `os.Pipe` 并手动关闭写端，本身没有这个问题。

## 七、验证情况

- Linux 开发侧：`go test ./internal/selftest/` 全绿（19 项：通过 16、跳过 3——ST15 渲染
  依赖 Win32 GDI、ST16 无模型配置时跳过），`-count=8` 连跑稳定。
- 交叉编译：`GOOS=windows GOARCH=amd64/386 CGO_ENABLED=0` 均通过，产物在 `dist/`。
- 真机（Win7 SP1）：本轮改动不含 Win32 专属逻辑，渲染与命令执行路径沿用 v1.19 已验证实现；
  仍需在真机上跑一次 `win7harness.exe -selftest` 确认 19 项全绿，报告可直接回传。
