WIN7 Harness v1.29.0 迭代说明

版本定位：把 v1.28 的"人走了也管得住、出了事查得清"，补成"管得住还能改得动、改之前先测得住"。

适用环境：Windows 7 SP1 + KB2533623 + KB4474419，单文件 exe，零运行库依赖，不装 .NET、不装 VC++、不写注册表。

包名：WIN7Harness-v1.29.0-win7.zip（内含 x86 / x64 双架构 exe、README、setup.bat）。

本版只加能力、不改旧行为：不加参数启动时仍然一次监听都不开、定时任务为空、守护规则为空，与 v1.28 完全一致。

本版四批（A/B/C/D）一并落地，下面按批说明。

----------------------------------------------------------------
一、A-1 自更新闭环（/update apply）
----------------------------------------------------------------

过去：/update 只能"检查有没有新版本 + 下载校验"，下完就停在那儿，
      想真换版本还得手动关程序、替换 exe、重新打开，多数人干脆不升。
现在：下载 → 校验 → 暂存 → 确认 → 替换 → 重启 → 失败回滚，一条链打通。

  · 两步走，不许一步到位
      /update apply          下载并校验，只暂存，不动当前 exe
      /update apply force    才真替换
      多一道手，是因为"替换自己"这件事在 Win7 上没有第二次机会——
      脚本写错、文件被占用、杀软拦截，任何一步失败都可能留下一个打不开的 exe。

  · 校验三层
      清单里声明的 SHA256、下载后的实际 SHA256、以及**按当前进程自身 PE 头**再核一次架构。
      清单写对不等于文件对；把 amd64 的包装进 386 的进程，替换完直接起不来。
      核不过就放弃替换，并说明是"哪个环节对不上"。

  · 替换与回滚（ApplyScript）
      由 cmd 脚本执行：等本进程退出 → 把旧 exe 改名 .old → 移入新 exe → 启动 → 观察
      新进程 30 秒内没起来，脚本自己把 .old 改回去并重新拉起。
      脚本不依赖 PowerShell（Win7 上常被组策略拦），只用 cmd 内建命令。

  · 诚实边界
      替换期间窗口会关闭，会话与配置在用户目录里，不受影响；
      脚本路径与暂存路径都会打印出来，失败时用户能手动跑脚本补救。

----------------------------------------------------------------
二、A-2 任务队列（/queue）
----------------------------------------------------------------

过去：引擎正忙时到点的定时任务会被直接丢弃，只在界面上闪一句"忙，跳过"，
      人不在就彻底错过，而且事后无从查证。
现在：忙时入队，空闲自动接着跑。

  · 行为
      上限 64 条；入队项带来源（定时任务 / 目录守护 / 手机指令）与去重键；
      同一个到期点（计划 ID + 到期时间）只进一次，不会因为反复检查被刷成一屏；
      出队执行完才释放去重键，避免"刚取出还没跑完又被塞回来"。

  · 满了怎么办
      不静默丢弃：入队失败会带上原因（队列已满），并在界面提示。
      宁可告诉用户"没排上"，也不要让他以为跑了。

  · 指令
      /queue           看待执行清单（来源 + 摘要）
      /queue run       立即执行队首（正在生成时会提示跑完自动继续）
      /queue clear     清空，并报出丢弃了几条

----------------------------------------------------------------
三、A-3 手机停止任务（POST /api/stop）
----------------------------------------------------------------

过去：手机能发指令、能看输出，但停不下来；人在外面发现跑偏了，只能回电脑点停止。
现在：手机上点"停止"，等价于电脑上按停止。

  · 接口
      POST /api/stop     停止当前生成并清空队列，返回停掉了什么
      GET  /api/stop     405（不做只读语义的"停止"）

  · 话术有讲究（StopReport）
      真在跑：返回 stopped=true，并逐项列出"当前生成 / 队列中 N 个任务"；
      没在跑：返回 stopped=false，文案是"当前没有正在跑的任务"——
      不能返回一个假的"已停止"，让人以为刚才那个任务被拦下来了。

  · 老宿主
      未接停止能力时返回 503，手机端显示"该版本不支持远程停止"，
      不装作成功。

----------------------------------------------------------------
四、B-1 手机看计划、开关计划（/api/plans、/api/plan）
----------------------------------------------------------------

过去：定时任务只能在电脑上 /sched 里看和改，手机上完全不可见。
现在：手机计划 tab 列清单、一键启停。

  · 接口
      GET  /api/plans         计划列表（名称、时间规格、启用状态、已跑次数）
      POST /api/plan          {"id":"...","on":true|false} 启停
      列表按名字稳定排序（同一口径，刷新顺序不跳）；
      缺 id 返回 400；id 不存在返回 ok:false + 原因，不当 500 报错。

  · 为什么不给手机加"新增计划"
      新增要写 cron 表达式与提示词，手机键盘上写错一次就是一条永远不跑的规则；
      启停是"要不要跑"，改是"怎么跑"，前者适合手机，后者留在电脑。

----------------------------------------------------------------
五、B-2 设备管理（/api/devices、/api/revoke、/device）
----------------------------------------------------------------

过去：配对 token 只在内存里，重启就全失效，手机每次都得重新扫码；
      也没有"这台是谁、什么时候用过、要不要踢掉"的地方。
现在：设备表落盘 + 电脑端与手机端都能管。

  · 落盘（LoadDevices / DevicesFile）
      只存 token 的哈希，不存明文；文件里出现明文即视为实现错误，自检 ST73 会拦。
      记录名称、最近使用时间、到期时间；重载后旧 token 仍然认，
      重启电脑手机不用重新扫码。

  · 清理与吊销
      过期设备自动清（Prune），不影响有效设备；
      吊销按名称或 ID（/device revoke 小马手机），
      注意：吊销会同时清掉内存里的 token，否则本次进程内还能继续用。

  · 接口
      GET  /api/devices    设备列表 + 当前 token 尾部 4 位（用于认出"这条是我"）
      POST /api/revoke     踢设备（GET 一律 405，防止被一条链接踢下线）

----------------------------------------------------------------
六、B-3 运行指标（/perf、GET /api/metrics）
----------------------------------------------------------------

过去：慢在哪、失败率多少、内存吃了多少，只能靠感觉。
现在：工具耗时分位 + 失败计数 + 运行画像，电脑与手机同一份数据。

  · 采集
      每次工具调用记一条（工具名、耗时、成功/失败）；回合结束记 turn_end / error；
      环形缓冲上限 2048 条，不随会话增长。
      只记名字与耗时，不记参数与输出内容（隐私优先）。

  · 输出（MetricsText）
      按工具聚合成 count / fail / P50 / P95，附堆内存、系统内存、goroutine 数。
      P95 用的是排序后取位，不是平均——平均值会把"偶发 5 秒"抹平。

  · 用法
      /perf           看当前指标
      /perf clear     清零重来
      手机的 /api/metrics 返回同一份快照；诊断包也会多一份 metrics.txt。

----------------------------------------------------------------
七、C-1 可测核心从 app 包里拆出来
----------------------------------------------------------------

过去：app 包带 windows build tag，Linux 开发机上跑不了测试，
      于是命令解析（/update 的 apply/force、/queue 的 clear/run、/device 的 revoke/prune）
      这类分支密集的代码，一直靠手点验证——改一行，全靠记性。
现在：纯逻辑搬到 core，`go test` 能直接覆盖。

  · 拆了什么
      UpdateCmd / QueueCmd / DeviceCmd（子命令解析）
      StopReport / PlanToggleText（回执话术）
      profileFor / MemProfile（内存档位，见 D 批）

  · 怎么保证拆完没走形
      app 侧只留"取到参数 → 调 core 解析 → 按结果分支"，解析规则只有一份；
      core 侧用表驱动单测覆盖各种写法（中英文、大小写、缺参、多余参数）。

八、C-2 忽略错误审计
----------------------------------------------------------------

把仓库里显式丢弃返回值的地方做了一次盘点（合计 199 处：生产代码 192、测试代码 7），
按"丢掉了会怎样"分类，只修真正会让用户吃亏的那几类：

  · 已修（本版）
      会话落盘前的 .bak 备份写失败 —— 过去静默，等于把兜底悄悄摘掉；现在写日志。
      /eval 报告与 JSON 报告写失败 —— 过去无论成没成都打印路径，用户去找是空的；现在如实说"未能落盘"。

  · 有意保留（并写清理由）
      崩溃标记文件、技能"已提示过"标记 —— 写不成只影响下次是否再提示，不影响正确性；
      HTTP 响应编码 —— 对端已断开，写失败没有补救动作；
      清理类（os.Remove / RemoveAll）—— 残留最多多占几 MB，不值得为它中断主流程。

  完整分类与逐条理据见 docs/审计-忽略错误-v1.29.0.md。

----------------------------------------------------------------
九、C-3 配置与清单损坏兜底
----------------------------------------------------------------

过去：config.json / 定时清单 / 设备表解析失败时当空表处理，
      用户的设置与计划"凭空消失"，且没有任何证据留下。
现在：坏文件挪到 .bad-<时间戳> 备份，原因留在 LoadErr 里，界面提示一次。

  · 行为
      配置坏 → 按默认配置继续启动（不瘫痪），原因只播报一次，不反复弹；
      定时清单坏 → 清单置空 + LoadErr，界面提示"清单损坏，已备份到 xxx"；
      文件不存在 → 首次启动的正常情况，不报错、不留备份。

  · 为什么留备份而不是直接覆盖
      坏文件里往往还留着用户手写的提示词、时间规格，能人工救回来；
      直接覆盖就真没了。

十、D 内存画像三档自动收紧
----------------------------------------------------------------

过去：只有"手动开低内存模式"一档，老机用户不会主动去点，
      等他因为 OOM 来找你时已经没法用了。
现在：按物理内存自动分三档，手动开关仍最高优先。

  · 档位（MemProfile）
      2G 及以下：低内存档 —— @ 引用 48KB、工具输出 96KB、索引 1200 文件 / 6000 符号、
                  图片最长边 1024、单张 640KB、每条消息 2 张、子任务并发 1
      4G：中等档 —— 80KB / 160KB / 2000 / 12000 / 1280 / 900KB / 3 张 / 2
      8G+：标准档 —— 120KB / 256KB / 3000 / 20000 / 上限尺寸 / 3 张 / 3

  · 探测失败怎么办
      读不到物理内存（极老系统、被安全软件拦）时按"未知"档走中等预算，
      不猜成高配——猜高的代价是崩溃，猜低的代价只是慢一点。

  · 索引上限成为天花板
      maxFiles / maxSymbols 不再写死生效值，只作为天花板，实际取 min(档位预算, 天花板)。
      换内存量不需要改代码，/index 重建后即按新档运行。

十一、自检
----------------------------------------------------------------

本版自检从 70 项扩到 77 项，新增 ST71–ST77 共 7 项，全部为新能力真跑（真端口、真文件、真数据）：

  ST71  手机停止任务 —— 空闲不谎报、运行中真停、GET 405、未接能力 503、无 token 401
  ST72  手机计划与设备管理 —— 列表稳定排序、缺 id 400、无效 id ok:false、GET 吊销 405
  ST73  设备表落盘与吊销 —— 无明文、重载可验、过期拒绝、Prune 不误伤、吊销即断、坏文件留 .bad-
  ST74  运行指标与耗时画像 —— 100 次采样 P50/P95 对齐、失败计数、/api/metrics 内容可见
  ST75  任务排队不丢 —— 上限拒绝、FIFO、未完成不放行同键、Done 后可再入、清空计数
  ST76  更新暂存与架构校验 —— 386/amd64 识别、错架构与非 PE 拒绝、暂存读回、脚本含 wait/rollback/giveup 且不依赖 PowerShell
  ST77  配置与清单损坏留证 —— 坏清单挪走 + LoadErr、文件缺失不报错、坏配置按默认启动且原因只播一次

运行结果：合计 77 项，通过 74，失败 0，跳过 3。
跳过项：ST40（环境未装 git），以及两项依赖 Windows 实机/外网的用例。

修掉的两处真问题（自检与交叉编译各揪出一个，都是"编译过了但真机跑不通"那一类）：
  · profile_windows.go 重复声明 memoryStatusEx，windows 目标直接编译失败；
    改为复用 checks_windows.go 里已有的 kernel32 proc。
  · 工具成败判断写成 ev.Err == ""（Err 是 bool 不是 string），
    会让每次成功都被记成失败；改为 !ev.Err。

自检跑法（Linux 侧回归，先于交叉编译）：
  go run ./cmd/selftest_run <沙箱目录>
注意：必须带沙箱目录参数，不带会直接 panic（v1.28 踩过的坑，本版依旧）。

十三、遗留与已知限制
----------------------------------------------------------------

  · 自更新替换链路只在 Linux 侧做了脚本与架构校验的自检，真机换版本仍需实机走一遍；
  · 回滚判定是"新进程 30 秒内没起来"，极慢的机械盘冷启动可能误判为失败并回滚（回滚是安全方向）；
  · 任务队列上限 64 条且不落盘：程序重启后排队任务不恢复（定时任务本身会按补跑规则重来）；
  · 手机端只能启停计划，不能新增/编辑计划与提示词（有意为之）；
  · 运行指标是进程内环形缓冲，重启清零，不做历史趋势；
  · 内存档位只在启动时探测一次，运行中物理内存变化（热插拔/虚拟机调整）需重启生效；
  · ST40 Git 提交与回滚闭环仍未在 Win7 实机验证，Linux 侧因无 git 跳过。
