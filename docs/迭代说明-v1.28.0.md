WIN7 Harness v1.28.0 迭代说明
================================================================

版本定位：把 v1.27 的"人走了活还在跑"，补成"人走了也管得住、出了事查得清"。
两批一起做（用户拍板 A+B）：

  A 批 指挥台 2.0——扫码配对、手机看会话与输出、手机审批回传、可选 HTTPS、断线续传；
  B 批 稳定性收尾——定时任务关机补跑、守护静默窗口、桌面通知与托盘、失败自动诊断。

适用环境不变：Windows 7 SP1 + KB2533623 + KB4474419，单文件 exe，零运行库依赖，
不装 .NET、不装 VC++、不写注册表。
包名：WIN7Harness-v1.28.0-win7.zip（内含 x86 / x64 双架构 exe、README、setup.bat）。

本版只加能力、不改旧行为：不加参数启动时仍然一次监听都不开、定时任务为空、
守护规则为空，与 v1.27 完全一致。

----------------------------------------------------------------
一、A-1 扫码配对（/remote qr）
----------------------------------------------------------------

过去：/remote on 之后要念 6 位配对码给旁边的人，或者自己在手机上一位一位敲，
      码还有 5 分钟时限，念错一位就得重来。
现在：电脑屏幕上直接画二维码，手机相机一扫就打开指挥台并完成配对。

  · 怎么用
      /remote on          先开指挥台（默认只监听局域网）
      /remote qr          窗口中央画出二维码，Esc 或再敲一次收起
      二维码里编码的是带配对码的完整地址，扫码即配对，不用手输。

  · 为什么自己写二维码编码器
      Win7 上不能依赖第三方库，也不想为了一个二维码引入 WebView2 或在线 API。
      internal/qr 是纯本地实现：Reed-Solomon 纠错、掩码罚分选择、版本自动选择，
      不联网、不上传地址（指挥台地址本身就属于敏感信息）。
      自检 ST61/ST62 校验矩阵结构不变量与掩码选择，不是"能画出来就算过"。

  · 安全边界没变
      配对码仍是 6 位、5 分钟有效、用一次即作废；二维码只是把"输码"换成"扫码"，
      没有放宽任何鉴权。二维码面板上同时印出明文配对码，方便扫不了码时手输。

----------------------------------------------------------------
二、A-2 手机看会话与输出（GET /api/convs、/api/conv）
----------------------------------------------------------------

过去：手机端只能看到"当前任务在跑"，看不到跑了什么、输出了多少，
      想知道进展还是要回电脑前。
现在：手机浏览器里能列出最近会话，点进去按行读输出。

  · 接口
      GET /api/convs?limit=20          最近会话列表（标题、时间、大小）
      GET /api/conv?id=<会话ID>&from=0&max=200
                                       从第 from 行起最多取 max 行

  · 只读、有上限
      两个接口都只读会话文件，不改、不删、不执行。
      limit 与 max 都有硬上限，防止一个大文件把手机流量和内存打满；
      返回体带 next 游标，前端按需继续拉。

  · 不含密钥
      会话正文按原样读取，但配置与 Key 不在会话文件里，接口不额外暴露配置。

----------------------------------------------------------------
三、A-3 手机审批回传（/remote approval on|off）
----------------------------------------------------------------

过去：v1.27 明确写了"手机上点不了同意"，高危操作必须回电脑确认。
      人在外面时，任务就卡在确认弹窗上等。
现在：可选用手机审批，两边谁先点谁生效。

  · 开关
      /remote approval on     高危操作同时推到手机
      /remote approval off    回到只在电脑上确认（默认）
      开关状态落盘（remote_approval），重启后保持。

  · 机制
      电脑端弹窗照常弹，同时生成一条待审批项（AskApproval），
      手机 GET /api/approvals 看到待办，POST /api/approve 回填结果。
      手机等待上限 10 分钟（ApprovalTimeout），超时只影响手机侧，
      电脑端弹窗不受影响，仍然可以正常批准或拒绝。
      两边同时点，先到的那个生效，另一个返回"已处理"，不会重复执行。

  · 默认关闭的理由
      审批是最后一道闸。默认关，是为了让"开"这个动作必须被人明确做过一次，
      并且知道开了之后手机也能放行。界面状态栏会显示"手机可审批"，不会让你忘了它还开着。

----------------------------------------------------------------
四、A-4 可选 HTTPS（/remote https on|off）
----------------------------------------------------------------

过去：指挥台走明文 HTTP，同一 Wi-Fi 下抓包就能看到指令原文。
现在：可一键切到 HTTPS，自签证书，本地生成，不需要域名、不需要联网申请。

  · 怎么用
      /remote https on    生成/复用自签证书并重启监听（https://…）
      /remote https off   回到明文 HTTP
      配置项 remote_https 落盘；切换后已配对的手机需要重新扫码（token 随服务重启失效）。

  · 自签证书的实话
      手机第一次打开会提示"证书不可信"，点「继续访问」即可——这是自签名证书的正常现象，
      不代表被中间人攻击。反过来，如果哪天你在自己家 Wi-Fi 下看到这个提示变成了
      "证书颁发者异常"，才需要警惕。
      证书覆盖本机所有局域网 IP 与 localhost（CertHosts），有效期由 SelfSignedCert 控制。

  · 边界
      不做公网穿透、不做 CA 申请、不做证书自动续期。HTTPS 只解决"同网段被嗅探"，
      解决不了"把端口映射到公网"带来的风险。

----------------------------------------------------------------
五、A-5 断线续传（游标拉取）
----------------------------------------------------------------

过去：手机锁屏、切后台、Wi-Fi 抖一下，回到页面就要从头再拉一遍输出，
      长任务下等于白等。
现在：按行游标拉取，断在哪从哪继续。

  · 用法
      首次 from=0 拉一批，返回体里带 next；
      断线回来后带着 next 继续请求，已读的部分不重复传。
      会话切换或服务重启后游标失效，接口返回明确的"游标过期"，前端自动回到 from=0，
      不会卡在空白页。

  · 为什么不做 WebSocket
      零依赖底线 + Win7 上的兼容性，长连接不如"短请求 + 游标"稳。
      手机端锁屏时连接本来就会被系统掐掉，游标天然适配这种场景。

----------------------------------------------------------------
六、B-1 定时任务关机补跑（DueCatchup）
----------------------------------------------------------------

过去：机器关机、睡眠，或者引擎正忙，到点的定时任务就静默跳过，
      而且下次正常触发时你完全不知道中间漏了几次。
现在：启动后补跑最近一次，并把"漏了几次"讲清楚。

  · 行为
      每分钟检查一次，发现"上次应跑时间已过但没跑"，就补跑一次；
      补跑只跑一次，不把错过的 N 次全部堆上来（堆上来只会刷屏并抢引擎）；
      漏跑超过 1 次时，指令前会加一句补跑说明，界面同时提示
      "错过了 N 次，已合并为一次"。

  · 刻意不做的事
      不补跑"已经过期很久"的任务（例如三天前的一次性任务），
      只按最近一个到期点补，避免开机后一口气跑一堆历史任务。

----------------------------------------------------------------
七、B-2 守护静默窗口（/watch gap）
----------------------------------------------------------------

过去：目录守护有 Debounce，解决的是"一次改动还没停下来"。
      但"刚跑完又改了下一处"这种情况，Debounce 挡不住——一个批量改文件的脚本
      能让规则连续触发十几次。
现在：每条规则可单独设最小间隔（MinGapSec）。

  · 用法
      /watch gap 1 30     第 1 条规则，两次触发至少隔 30 秒
      /watch gap 1 0      不设限（等价于只靠 Debounce）
      默认 30 秒；配置随规则落盘（min_gap_sec）。

  · Debounce 与 MinGap 的分工
      Debounce 管"改动还在继续"，MinGap 管"改动已经结束但马上又来了下一批"。
      两个都设，才既不会半截就跑，也不会被连续改动刷爆。

----------------------------------------------------------------
八、B-3 桌面通知与托盘
----------------------------------------------------------------

过去：任务跑完、定时触发、任务失败，只有界面里的一行提示，
      人不在座位上就等于没看见。
现在：托盘气泡通知 + 托盘常驻。

  · 通知范围
      任务完成、任务失败、定时任务触发，这三类才弹，不弹中间过程。
      气泡只放一句话（取正文最后一行非空内容），完整内容仍在会话里。
      失败用错误样式，避免和成功混在一起扫一眼看不出。

  · 退化路径
      托盘不可用（部分 Win7 精简系统）时不报错、不静默，
      退回界面内提示，能力降级但不断链。

  · 托盘懒创建
      托盘要等窗口创建后才能挂，所以是首次需要时创建，不在启动路径上加阻塞。

----------------------------------------------------------------
九、B-4 失败自动诊断（/diag 与自动导出）
----------------------------------------------------------------

过去：任务失败，用户能提供的只有一句"跑挂了"，日志在哪、什么版本、什么配置都得现问。
现在：失败即留证据，一个 zip 打包带走。

  · 自动
      真失败时自动导出诊断包（autoDiag），并做了冷却，
      避免同一个错误反复打包把磁盘塞满。

  · 手动
      /diag     随时打一份当前状态的诊断包（diagQuick）

  · 包内容（core.ExportDiag / DefaultDiagOptions）
      checks    自检结果摘要
      config    脱敏后的配置（API Key 不出现明文）
      logs      最近日志
      env       系统与运行环境信息
      sessions  最近 20 个会话文件的名称与大小（不含正文）

  · 隐私口径
      全为本机只读采集，不含对话正文、不含密钥明文。
      打包路径会直接显示在界面里，方便你决定发不发、发给谁。

----------------------------------------------------------------
十、自检
----------------------------------------------------------------

本版自检从 60 项扩到 70 项，新增 ST61–ST70 共 10 项，全部为新能力真跑：

  ST61  二维码矩阵结构不变量（定位图形、时序图形、格式信息位置）
  ST62  掩码与罚分选择（不是"能编码"就算过，要对齐标准罚分规则）
  ST63  扫码配对地址（地址拼接、配对码编码正确）
  ST64  指挥台自签 HTTPS（证书可用、握手可通）
  ST65  手机查看会话与输出（列表、分页、游标）
  ST66  手机审批回传（双向、先到先得、超时不污染电脑端）
  ST67  断线重连续传（游标续拉、过期回退）
  ST68  定时任务关机补跑（漏跑统计、只补一次）
  ST69  守护静默窗口合并（连续改动不被放大）
  ST70  失败诊断包与配置落盘（包内容齐全、配置项往返）

运行结果：合计 70 项，通过 67，失败 0，跳过 3。
跳过项：ST40（环境未装 git）、以及两项依赖 Windows 实机/外网的用例。

自检跑法（Linux 侧回归，先于交叉编译）：
  go run ./cmd/selftest_run <沙箱目录>
注意：必须带沙箱目录参数，不带会直接 panic（本版踩过的坑）。

十一、构建与产物
----------------------------------------------------------------

  OUT_DIR=<目录> ./build.sh   指定 ZIP 输出目录
  FORCE_ICON=1 ./build.sh     强制重绘图标

产物：WIN7Harness-v1.28.0-win7.zip
  内含 win7harness-amd64.exe、win7harness-386.exe、图标、README.txt、
  setup.bat、make-portable.bat。

Go 版本固定 1.20.14（Win7 支持的最后版本），build.sh 会强制校验，
用高版本编译出来的 exe 在 Win7 上会直接起不来。

----------------------------------------------------------------
十二、遗留与已知限制
----------------------------------------------------------------

  · ST40 Git 提交与回滚闭环仍未在 Win7 实机验证，Linux 侧因无 git 跳过；
  · 自签 HTTPS 在 Win7 + IE/旧版 Android 浏览器上的提示文案差异，需实机确认；
  · 手机审批只覆盖"高危操作确认"，不覆盖工具参数逐段审阅；
  · 诊断包不含对话正文（隐私优先），排查语义问题时仍需用户口述上下文；
  · 补跑只按最近一个到期点，长期关机后不会补齐历史全部任务（有意为之）。
